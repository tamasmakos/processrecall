## The design that won

Air-gapped delivery of GraphKnows as a private versioned wheel plus a client-operated deployment compose, with a self-contained release image, runtime-enforced offline mode, and re-ingest-only upgrades. Four settled parts, made concrete against the code:

(1) PRIVATE WHEEL, NO PUBLIC PYPI, NO HTTP SURFACE.
Seam: `.github/workflows/release.yml`, the `publish` job. Today it downloads CI's `dist/` artifact and hands it to `pypa/gh-action-pypi-publish@dc37677...` under `id-token: write` (release.yml:24-70). The change: drop the `pypa/gh-action-pypi-publish` step and the `id-token: write` permission, and publish the same `dist/*.whl` bytes as an asset on the private repo's GitHub Release for the pushed `v*` tag. No private index, no artifact registry, no new dependency — the wheel's only consumer is the release image build in the same workflow, so an index would be infrastructure for one hop. Everything else in that job stays: the tag/`_version.py` equality check, and "publish builds nothing, it consumes CI's artifact".
Interface changed: the release contract. `tests/test_release_workflow.py::test_publishes_via_trusted_publisher_sha_pinned_no_stored_token` (line 163) and `::test_id_token_write_is_scoped_to_the_publish_job_only` (line 186) both pin the PyPI path and must be rewritten to pin the private path instead — that is the visible, deliberate cost, not a silent relaxation. `docs/versioning.md` and any README install line naming PyPI move with it.
No HTTP surface: nothing new is added; this is the standing statement that the deployment exposes only ArcadeDB inside the compose network and the library API, not a web/MCP port.

(2) OFFLINE = AIR-GAPPED, ENFORCED BY RUNTIME CONFIGURATION.
Seam: image ENV + deployment compose `environment:`, not Python call sites. `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `HF_DATASETS_OFFLINE=1` and `NLTK_DATA` pointing at the baked corpora path are declared once as `ENV` in the release Dockerfile and mirrored in the deployment compose's env anchor. Deliberately NOT a `GraphKnowsSettings` field: a settings field is a per-process convention that a stray subprocess or a library import escapes, whereas process ENV inherited from the image cannot be. This is greenfield — `HF_HUB_OFFLINE` appears today only as a comment in `rdf_io.py:11-14`/`bake_models.py:51` and as `os.environ.setdefault` local to `_nltk_corpora` in `scripts/bake_models.py:251`; that local setdefault stays as-is (it makes the `--check` path honest even outside the image).
The egress-blocked test: one new `tests/test_offline.py` using a `monkeypatch`ed `socket.socket.connect` that raises on any non-loopback address, wrapped around the `llm_free` ingest+retrieve path (loopback stays open so the ArcadeDB service in the dev stack still works). ~15 lines, stdlib only, no `pytest-socket` dependency. It fails if any code path reintroduces a model/corpus fetch.
Existing boot preflight is reused unchanged: `scripts/docker-entrypoint.sh` already runs `scripts/bake_models.py --check`, which fails the container if weights are absent — with egress blocked that is exactly the "loud failure instead of silent download" behaviour we want.

(3) SELF-CONTAINED RELEASE IMAGE, SEPARATE FILES.
Seam: two NEW files — `Dockerfile.release` and `docker-compose.release.yaml`. The existing `Dockerfile` (single-stage, dev-only, bind-mount premise, Dockerfile:1-3) and `docker-compose.yaml` (dev-only, :1-5) are not modified. This is not stylistic: `tests/test_repo_hygiene.py` reads `DOCKERFILE = REPO_ROOT / "Dockerfile"` (line 37) and asserts `HEALTHCHECK`, `HF_HUB_OFFLINE`, `AS builder|models|runtime|dev` are absent from it (:129-142). Putting the release image in its own file keeps that test true to its own premise (#203 collapsed the *dev* image to one stage) instead of relaxing it. If a later reviewer wants those assertions extended to `Dockerfile.release`, that is a separate, argued change.
`Dockerfile.release` shape: `FROM python:3.13-slim`, `pip install` the wheel from (1) — not the source tree, so the image is provably built from the shipped artifact — then `RUN python scripts/bake_models.py` to download weights at build time (the last step allowed to touch the network), then the offline ENV of (2), the existing non-root `graphknows` user, and `scripts/docker-entrypoint.sh` as ENTRYPOINT. No new model-enumeration logic: `scripts/bake_models.py::_model_ids` (:36-53) already resolves every model id from the code that owns the choice. `scripts/preflight.py`'s stale-image guard needs no change — it already no-ops when there is no bind-mounted source (:79-81), which is precisely this image.
`docker-compose.release.yaml`: the pinned `arcadedata/arcadedb` service with its heap settings, plus the graphknows service on the release image with the same `GRAPHKNOWS_*` env anchor as dev minus the dev-only bits (no bind mount, no source volume), plus the offline ENV. No `build:` key — the client pulls/loads an image, they do not build.

(4) UPGRADES ARE RE-INGEST; VERSION-STAMPED NAMESPACE THAT REFUSES ON MISMATCH.
Seam: `GraphStore.ensure_schema(dims)` at `graphknows/storage/arcadedb/graph_store.py:370`, the single load-time path every runtime crosses (`graphknows/memory.py:155`, inside `_build_retriever`). Verified: `graphknows/storage/namespace.py` (62 lines) does pure name resolution and holds no version state today; there is no `schema_version` anywhere in the package.
Change: add one singleton vertex type to `_CORE_DDL` in `graphknows/storage/arcadedb/_schema.py` (e.g. `NAMESPACE_STAMP` with a unique `id` property and a `version` property). `ensure_schema` reads the stamp before applying DDL: absent -> apply DDL and write the current `graphknows.__version__`; present and equal -> proceed; present and different -> raise a dedicated `NamespaceVersionMismatch` (new, in `graphknows/exceptions.py`) naming the stamped version, the running version, and the remedy ("drop the namespace and re-ingest"). No forward migrations, no auto-drop — refusing is the whole behaviour. One test: stamp a namespace, bump the version, assert the raise.
This is one function doing one thing (the stamp check lives in a small `_check_stamp` helper called from `ensure_schema`), no new module, no new abstraction.

TENSOR BRAIN / TOUCHED SURFACE: this change is delivery and construction; nothing here maps onto a TB concept, so nothing is renamed and no new channel is introduced. Files touched: `.github/workflows/release.yml`, `tests/test_release_workflow.py`, new `Dockerfile.release`, new `docker-compose.release.yaml`, new `tests/test_offline.py`, `graphknows/storage/arcadedb/_schema.py`, `graphknows/storage/arcadedb/graph_store.py`, `graphknows/exceptions.py`, docs. Not touched: `Dockerfile`, `docker-compose.yaml`, `tests/test_repo_hygiene.py`, `scripts/bake_models.py`, `scripts/preflight.py`, `scripts/docker-entrypoint.sh`.

EXTRAS: no new extra is introduced. `MissingExtraError.KNOWN_EXTRAS` (`graphknows/exceptions.py:36`) stays `{assisted, langgraph, srl}`. If the release image later needs a deploy-only optional group, it follows the `observability` precedent — declared in `pyproject.toml` only — unless a `MissingExtraError` call site names it, in which case both `pyproject.toml` and `KNOWN_EXTRAS` change together and `tests/test_packaging.py` (:93, :116) enforces it. The brief's `tests/test_extras.py` does not exist; the enforcement is in `tests/test_packaging.py`.

OUT OF SCOPE, not pulled in: epic #135 symbolic-channel correctness, and the library-wide no-silent-degradation policy.

Known risks: The namespace stamp is specified as graphknows.__version__, so every patch release refuses to open existing graphs and forces a full re-ingest at an air-gapped client where that is a manual operation. Confirm before specifying; a hand-bumped graph-format constant is the alternative.; Rewriting tests/test_release_workflow.py:163 and :186 removes the assertions that guard against a stored PyPI token. The replacement must pin the private path just as tightly, or the change reads as a weakened test.; Two Dockerfiles and two compose files drift: the dev stack and the release image can diverge on ArcadeDB version, heap settings or GRAPHKNOWS_* defaults with nothing catching it. ## Prototype

Question: Does a container built FROM the wheel with HF_HUB_OFFLINE=1/TRANSFORMERS_OFFLINE=1 and baked weights actually complete an llm_free ingest+retrieve with `--network` restricted to the compose network only — i.e. does any library path still reach for HuggingFace, NLTK or spaCy data at first use rather than at bake time? Only running it settles which fetches bake_models.py's --check does not cover.

Verdict: **Confirmed for every code path actually exercised: with HF_HUB_OFFLINE=1/TRANSFORMERS_OFFLINE=1/HF_DATASETS_OFFLINE=1 set and a socket-level block on every non-loopback connect() active for the whole process, the REAL runtime call sites (not bake_models.py) loaded cleanly with zero blocked-egress hits: the embed model (SentenceTransformer, BAAI/bge-small-en-v1.5), the relation verifier weights (huggingface_hub.hf_hub_download/snapshot_download, called directly from graphknows/ingestion/extraction/relations/_gliner2_verifier.py at ingest time — not just from bake_models.py), and the verifier's frozen encoder (transformers AutoModel/AutoTokenizer, microsoft/deberta-v3-base). This is exactly the gap the design flagged bake_models.py --check as not covering, and it holds up: offline mode is honoured by the actual runtime, not merely by --check's explicit local_files_only kwarg. However, I could NOT observe a full ingest_memory+recall_memory round trip complete within a reasonable prototype time budget in either --block or --no-block mode — both stall 10+ minutes at the identical point (right after the embed model, into GLiNER relation extraction) with steadily climbing CPU/RAM. Running the --no-block control ruled out a retry-storm caused by the egress block itself (identical stall shape with no block active), so this is this CPU-only dev machine being slow at stacked large-transformer inference, not a network-egress problem. So: no evidence of any offline-mode leak was found anywhere the pipeline actually reached; full end-to-end completion (through spaCy NER, ArcadeDB write, and the retrieve query) is unverified due to hardware speed on this box, not due to the design.**

What it showed: 1) bake_models.py --check already validates offline loading (local_files_only) for relex/embed/verifier/verifier-enc/spacy/nltk individually with clean pass/fail diagnostics. 2) The real runtime path (Memory.ingest_memory, not bake_models.py) also respects HF_HUB_OFFLINE/TRANSFORMERS_OFFLINE for every model it reached under an active socket-level egress block: embed model, relation verifier snapshot download, and verifier encoder all loaded successfully with the block armed and zero BLOCKED-egress exceptions raised. 3) A local-env quirk unrelated to the design: .env pins GRAPHKNOWS_ARCADEDB_URL to the compose-network hostname "arcadedb", which doesn't resolve on the bare host — had to override via env for local runs; not a design issue. 4) A pre-existing local-env bug (gliner 0.2.24 vs required >=0.2.26) made the vendored relex model fail to load with 'Unknown relation mode: none' until `pip install -e .` picked up the pinned floor — an environment defect, not a design defect. 5) Full pipeline completion (GLiNER relation extraction inference onward) is CPU-bound and did not finish within budget on this dev machine in either blocked or unblocked mode — confirmed as inference speed, not a network-retry artifact, via the identical-shape stall in the --no-block control run.
