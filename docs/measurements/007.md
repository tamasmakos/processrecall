# 007 — held-out traversal measurement (FR-036, SC-010)

Every retrieval path this feature adds, measured against the baseline path on a held-out
temporal split, and published whichever way it falls. No traversal reaches a reader before it
appears here: `ADMITTED` in `processrecall/guidance/fusion.py` names one traversal at a time, by
hand, as this file publishes it clearing the margin.

FR-031 names two further paths this run does not measure: the bounded multi-hop walk over
procedural and semantic edges (`ppr_neighbourhood`, T098) and the completion of the last-k step
window against recurring step subsequences (T099). Neither is implemented in
`processrecall/guidance/paths.py` yet — both are future tasks, dark until their own gate clears
them — so there is no admission-ranked candidate list for either to measure here.

## The run

| | |
| --- | --- |
| Corpus | the maintainer's own recorded prompts, `~/.processrecall/episodes.db`, read-only — 583 recorded prompts |
| Split | temporal, by prompt start instant: the earliest 70% of prompts train, the rest are held out |
| Asks | one per held-out step: the position the agent stood at, scored on the move it then made |
| Command | `uv run python scripts/measure_traversals.py ~/.processrecall/episodes.db` |
| Taken at | 2026-09-20, commit `978b932`, CPython 3.12.12 |
| Significance | exact two-sided sign test over per-ask reciprocal ranks, paired by ask |

plan.md's tradeoff for this script names `research/` as where the split lives, and the script's own
example points at `research/corpus.db`; no such corpus has been committed or published yet, so this
run reads the maintainer's live store instead. These numbers are therefore not independently
reproducible until a `research/corpus.db` exists — re-running this command against one, once it
does, is how another contributor checks them.

The `fused (every proposing traversal)` row's `p` is the sign test of that ranking against
`usual_next` — the headline comparison this report's conclusion rests on, tested the same way
every other row is. Each traversal below it contributes a pair of lines: its own ranking alone,
whose `p` is the sign test against the baseline, and the fused ranking with it removed, whose `p`
is the sign test against the full fused ranking above. `usually_refused` answers what to *avoid*
rather than what comes next, so next-move recall is the wrong question for it; its numbers are
recorded rather than read as an admission ranking, and `FUSED` in the harness keeps its edges out
of the fused pool.

## The baseline's place in the first-order band

`usual_next` alone puts the move actually taken first on **35.4%** of the 6,047 held-out asks.
That is where the next-command-prediction literature puts a first-order model: Davison & Hirsh
("Predicting Sequences of User Actions", 1998; "Experiments in UNIX Command Prediction", 1997)
report their best method, IPAM, reaching an average online predictive accuracy of up to 38%, with
most-recent-command at 30% and most-frequent-command at 18%, and a later survey lists IPAM at
39.9%. The baseline is therefore a healthy first-order Markov baseline, not a weak target: a
traversal that merely ties 0.354 has not earned admission, and its failure to beat the baseline is
the expected result rather than a defect. Gains are expected to come from a richer state alphabet
and higher-order sequence models, neither of which this feature ships.

## How each traversal falls

- **`after_change`, `on_entity`, `after_callers`** — 0.000 on all three metrics: they offered no
  candidate on any held-out ask, and removing each from the fused ranking leaves it unchanged. This
  is the harness, not the corpus: `Trained.of` folds the held-out graph through
  `graph.abstract.aggregate`, which never populates `AbstractGraph.precedes` — the
  `precedes_work_on` projection all three read is built only on the served-graph snapshot path
  (T043), which this script does not go through — so none of them can offer a candidate here
  regardless of what a held-out ask names, even though 3,156 of the 6,047 asks (52%) do carry a
  file. SC-010 is not actually measured for these three; their 0.000 records a harness gap, not a
  verdict on the traversals.
- **`usually_refused`** — 0.000 on all three metrics for a different reason: the training graph
  has no edge that earned the `REFUSED` pitfall, so it has nothing to offer regardless of position.
  This is a property of the held-out split's corpus rather than of the harness.
- **`generalised`** — 0.000 recall and MRR, but it did offer candidates: 22 of the 6,047 asks reach
  a node under `min_support` with an `is_a` parent, and on every one of those 22 the parent level's
  moves never ranked the taken move. Removing it from the fused ranking therefore does move the
  ranking on the asks where the two pools disagreed — which is why its `p` is 0.500 rather than the
  1.000 the never-firing traversals above show — even though the fused numbers with and without it
  round to the same three metrics. Its 0.000 is a measured result, not a coverage gap.
- **`prompt_start`** — 0.012 recall@1, 0.346 recall@5, 0.118 MRR alone, and the one traversal whose
  presence moves the fused numbers. It moves them **down**: removing it lifts fused recall@5 from
  0.679 back to 0.740 and MRR from 0.476 back to 0.526, exactly the baseline's, with p = 0.000. Its
  start-of-prompt moves are plausible openings that are wrong nearly everywhere mid-prompt, and
  they push the right answer down the ranking.
- **Fusing every proposing traversal** ties the baseline at recall@1 (0.354) and loses to it at
  recall@5 (0.679 against 0.740) and MRR (0.476 against 0.526).

## What ships

Zero traversals beat the baseline, so zero traversals are admitted: `ADMITTED` names `usual_next`
and nothing else, and the shipped default serves the baseline ranking. Every measured traversal
still runs and is still counted — `path_{traversal}` in `processrecall/guidance/paths.py` bumps for
every run whether or not the traversal is admitted, and `processrecall/guidance/render.py`'s
`path_{traversal}_used` counter separately credits only what is actually served — and its
candidates are reachable only through the off-by-default `unmeasured_traversals` setting. SC-010
asks for a recorded number against the baseline for every new path, and a fused result admitting
only what beats it. `generalised`, `prompt_start` and `usually_refused` each got a real held-out
ranking, whichever way it fell, and none beat `usual_next`, so their exclusion from `ADMITTED` is
earned. `after_change`, `on_entity` and `after_callers` did not get that ranking — their 0.000
above is a harness gap (see "How each traversal falls") — so SC-010 is unmet for those three in
this run even though they, too, stay out of the fused result by default.
